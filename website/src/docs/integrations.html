DEVELOPER FIELD GUIDE / 03

One Snag. Any number of apps.

Integration recipes for each kind of application: what to add, where it goes, how reporters are recognised, and what happens when browser data is cleared.

Choose how deep to integrate

Every application gets its own Snag project, with its own key and allowed origins. Each app then picks a level. The Snag side does not change between apps.

LevelWhat the app addsWhat the reporter getsUse it when
1. Script tagOne <script> tag. No server code.The widget. The reporter types a name and email, and My Tickets is kept per browser.Public sites, trials, apps you cannot change much.
2. Known userThe tag plus a few lines that pass the signed-in user to Snag.identify().Name and email filled in automatically. My Tickets is still kept per browser.Any app with its own login: POS, ERP, portals, internal tools.
3. Signed userLevel 2 plus one value signed on the app's server, passed next to the name and email. No new file or route.My Tickets follows the user to any browser, device or private window, and stays private per user on shared terminals.Shared terminals, users on several devices. See Level 3: signed users.

Level 1: the script tag

  1. In the dashboard, create a project for the app under Projects and copy its key.
  2. Add the app's origin, for example https://pos.example.com, to that project's allowed origins.
  3. Add the tag to every page, normally just before </body> in the base layout.
HTML
<script
  src="https://snag.example.com/widget.min.js"
  data-project-key="pk_your_project_key"
  data-mask-text="true"
  async
></script>

That is the whole integration. The project key is public and only accepted from the allowed origins. Never put an admin token or owner password in front-end code.

Single-page app with an env-var switch

Leave the variables empty and the widget is not loaded at all.

JAVASCRIPT · main.js
const snagApi = import.meta.env.VITE_SNAG_API_URL;
const snagKey = import.meta.env.VITE_SNAG_PROJECT_KEY;
if (snagApi && snagKey) {
  const s = document.createElement('script');
  s.src = snagApi.replace(/\/+$/, '') + '/widget.min.js';
  s.async = true;
  s.dataset.api = snagApi;
  s.dataset.projectKey = snagKey;
  s.dataset.maskText = 'true';
  document.head.appendChild(s);
}

Next.js with an env-var switch

A small server component keeps the key out of the layout and renders nothing when the variables are missing. The layout then gets one import and one <SnagWidget /> line.

JSX · components/SnagWidget.jsx
import Script from 'next/script';

export default function SnagWidget() {
  const api = process.env.NEXT_PUBLIC_SNAG_API_URL;
  const projectKey = process.env.NEXT_PUBLIC_SNAG_PROJECT_KEY;
  if (!api || !projectKey) return null;
  return (
    <Script
      id="snag-widget"
      src={`${api.replace(/\/+$/, '')}/widget.min.js`}
      strategy="afterInteractive"
      data-api={api}
      data-project-key={projectKey}
      data-mask-text="true"
    />
  );
}

Level 2: fill in the signed-in user

Name and email are labels on the ticket. They save the reporter typing and tell your team who reported it. There are two ways to pass them.

Server-rendered pages: data attributes

If the template already knows the user when the page is rendered, print them into the tag.

HTML TEMPLATE
<script src="https://snag.example.com/widget.min.js"
  data-project-key="pk_your_project_key"
  data-user-name="{{ user.full_name }}"
  data-user-email="{{ user.email }}"
  async></script>

Single-page apps: Snag.identify()

Call it after login, and clear it on logout so the next person at a shared device is not labelled as the previous one. The script loads asynchronously, so wait for window.Snag.

JAVASCRIPT
function withSnag(run) {
  if (window.Snag) return run();
  const timer = setInterval(() => window.Snag && (clearInterval(timer), run()), 500);
  setTimeout(() => clearInterval(timer), 15000);
}

// After login, with your own user object:
withSnag(() => window.Snag.identify({ name: user.name, email: user.email }));

// On logout:
withSnag(() => window.Snag.identify({ name: '', email: '' }));
  • When both name and email are set, the form shows “Reporting as …” instead of the two fields. When only one is set, the reporter can fill in the other.
  • Don't pass made-up placeholder addresses, such as user@app.local. Your team may try to email them.
  • Read the user from an endpoint or state the app already has. The integration should not change the app's login or business logic.

Worked example: a Next.js point-of-sale app

A real integration into an existing Next.js POS, done without changing any POS logic:

To switch the widget off, remove the two variables. To remove it completely, delete the two components and the two layout lines.

How Snag recognises a reporter

Snag does not create user accounts for reporters. On the first report the widget generates a random reporter token and keeps it in the browser's localStorage, under snag:rt:<projectKey>. Every widget request sends it, and the server returns only tickets with that project and token. Replies and live updates go to the same token. Name and email are labels only and do not decide who sees a ticket. The database stores only a one-way hash of the token, so a copy of the database cannot be used to read anyone's tickets through the widget. At level 3 the signed token takes the place of the browser token; see below.

What the reporter doesTokenMy Tickets in the widget
Normal reload or hard refreshKeptUnchanged
Clear cached images and files onlyKeptUnchanged. localStorage is not part of the HTTP cache.
Clear cookies and site dataDeletedEmpty. A new token is made on the next report.
Private or incognito windowTemporaryStarts empty and is lost when the window closes
Other browser, profile or deviceDifferentDoesn't show tickets from the other browser
When a token is lost, nothing is deleted. The tickets and conversations stay in the database and in the dashboard. The reporter can no longer see them in the widget, though, and replies sent afterwards on those tickets don't reach them. Contact them through the email on the ticket instead.

Shared devices

The token belongs to the browser profile, not to the person. On a shared terminal everyone who uses that profile sees the same My Tickets list, even with level 2, because identify() changes the labels and not the token. Level 3 solves this: each signed-in user gets their own list, whichever terminal they use. See Level 3: signed users.

Running many apps

  • One project per app. Each has its own key, allowed origins, team and tickets. This also keeps AMC reports per client.
  • Tokens are scoped per project. Even the same person in two apps has two separate ticket lists.
  • One widget build serves every app. All apps load widget.min.js from your Snag server, so a widget update reaches every app at once.
  • Set data-app-version from each app's release number, so reports show which build they came from.

Checklist for each new app

  1. Create the project and copy its key.
  2. Add every origin the app is served from: production, staging, and http://localhost:port for development.
  3. Add the tag at level 1, or the identity code at level 2.
  4. Open the app, press Alt+B, send a test report, and check that it appears in the Inbox.
  5. Reply from the dashboard and check that the reply appears in the widget.

Level 3: signed users

The app's server signs the logged-in user's id with a per-project secret. The widget sends the signed value instead of its browser token, and Snag checks the signature. The same user then gets the same ticket list in any browser, after clearing site data, in private windows and on any terminal, while other users at the same terminal see only their own.

Set it up

  1. Make sure the Snag server has SNAG_IDENTITY_KEY set; see Configuration.
  2. In the dashboard, open Projects, find the app, and under Signed reporters choose Generate secret. Copy it: it is shown only once.
  3. Put it in the app's server environment as SNAG_IDENTITY_SECRET. Never put it in front-end code or behind a NEXT_PUBLIC_ or VITE_ prefix.
  4. Add the signing function below where the app already knows the logged-in user, and pass the result with the name and email.
  5. Optional: once every user signs in before reporting, turn on Require signed to refuse anonymous reports.

Sign the user id (server side)

NODE.JS
import { createHmac } from 'node:crypto';

// Server-side only. Call it where you already know the logged-in user.
export function snagToken(userId) {
  const secret = process.env.SNAG_IDENTITY_SECRET;      // never NEXT_PUBLIC_ / VITE_
  const projectKey = process.env.SNAG_PROJECT_KEY;
  const id = String(userId);
  const expires = Math.floor(Date.now() / 1000) + 12 * 3600;  // max 7 days
  const sig = createHmac('sha256', secret)
    .update(`snag-identity-v1\n${projectKey}\n${id}\n${expires}`)
    .digest('base64url');
  return `v1.${Buffer.from(id).toString('base64url')}.${expires}.${sig}`;
}
PYTHON
import base64, hashlib, hmac, os, time

def snag_token(user_id):
    b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b"=").decode()
    uid, exp = str(user_id), str(int(time.time()) + 12 * 3600)
    msg = f"snag-identity-v1\n{os.environ['SNAG_PROJECT_KEY']}\n{uid}\n{exp}"
    sig = hmac.new(os.environ["SNAG_IDENTITY_SECRET"].encode(), msg.encode(), hashlib.sha256).digest()
    return f"v1.{b64(uid.encode())}.{exp}.{b64(sig)}"
PHP
function snag_token(string $userId): string {
    $b64 = fn($s) => rtrim(strtr(base64_encode($s), '+/', '-_'), '=');
    $exp = (string)(time() + 12 * 3600);
    $msg = "snag-identity-v1\n" . getenv('SNAG_PROJECT_KEY') . "\n$userId\n$exp";
    $sig = hash_hmac('sha256', $msg, getenv('SNAG_IDENTITY_SECRET'), true);
    return "v1." . $b64($userId) . ".$exp." . $b64($sig);
}
GO
func SnagToken(userID string) string {
	b64 := base64.RawURLEncoding
	exp := strconv.FormatInt(time.Now().Add(12*time.Hour).Unix(), 10)
	mac := hmac.New(sha256.New, []byte(os.Getenv("SNAG_IDENTITY_SECRET")))
	mac.Write([]byte("snag-identity-v1\n" + os.Getenv("SNAG_PROJECT_KEY") + "\n" + userID + "\n" + exp))
	return "v1." + b64.EncodeToString([]byte(userID)) + "." + exp + "." + b64.EncodeToString(mac.Sum(nil))
}

Pass it to the widget

HTML / JAVASCRIPT
<!-- Server-rendered template: one more attribute -->
<script src="https://snag.example.com/widget.min.js"
  data-project-key="pk_your_project_key"
  data-user-name="{{ user.name }}"
  data-user-token="{{ snag_token(user.id) }}"
  async></script>

// Single-page app: pass it with the name and email; clear it on logout
window.Snag.identify({ name: user.name, email: user.email, token: tokenFromYourServer });
window.Snag.identify({ name: '', email: '', token: null });

In Next.js the signing function can live in the same component that renders the script tag, as a 'use server' function passed to the client component that calls identify(). The worked example above does this, so no API route is added.

Security properties

ThreatWhat stops it
A user edits the token to read another user's ticketsThe HMAC-SHA256 signature covers the user id, expiry and project key, and is compared in constant time. Any change is rejected.
A token stolen from a browserIt expires: you choose the lifetime, up to 7 days, and 12 hours is recommended. Snag refuses longer-lived tokens and ends live streams when the token expires. The widget keeps the token in memory only, never in storage.
A token for app A used against app BEach project has its own secret, and the project key is part of the signed message.
A copy of the Snag database leaksThe secret is not in the database: it is derived from SNAG_IDENTITY_KEY in the server environment. Tickets store only one-way hashes of reporter identities. Neither can be used to forge or replay access.
The app's secret leaksChoose Rotate secret. The old one stops working immediately and other projects are unaffected.
Tokens showing up in proxy or server logsTokens travel only in the X-Reporter-Identity header. The live stream URL carries a random, single-use ticket that expires after 60 seconds.
A bad token quietly falling back to anonymous accessA request with an invalid signed token is refused outright (HTTP 401). It is never treated as anonymous.
Snag affecting the host appThe secret can only sign reporter ids for Snag; it grants nothing in your app. The signing code only reads your session. The widget runs in a closed Shadow DOM and never receives your app's cookies or session.
The app's own security still matters: Snag trusts whichever user id your server signs. Sign only the id of the session making the request, never an id taken from the request body or URL.

Error codes

Code (HTTP 401)Meaning
identity_invalidMalformed, tampered, signed with an old or wrong secret, or valid for more than 7 days
identity_expiredPast its expiry: issue a new token
identity_not_enabledThe project has no secret, or the Snag server has no SNAG_IDENTITY_KEY
